## 4. Cancel の振る舞いと試験

押したら、変換が次の通知の口（読み取りは全体の 1% ごと・値の展開と定義作りと書き出しはチャンネル 1 本ごと・段の境目）で旗を見て止まる。**止まる前の仕事は、作業フォルダ（出力先の中の一時の場所）にしか書いていない**ので、止めると作業フォルダが消えて終わり。公開（作業フォルダから最終の位置への入れ替え）の最中は止めず、入れ替えが終わってからログに出す。

|---|---|
| 読み取り中・値の展開・定義作り・書き出し中・ラップと検査・公開の直前（6 場面）に、**新しい出力先**へ変換して止める | 出力先は変換前と同じ（空）・作業フォルダも残らない・対応表（設定の置き場）も変わらない（自動成長の保存をしない）。止めた段の名前が分かる |
| 同じ 6 場面で、**既存の MES を置き換えようとして**止める | 既存の MES は **1 byte も変わらない**（変換前の出力先の写し = ファイルごとの SHA-256 と比べる）・作業フォルダも残らない |

## 6. GC による落ち方の発見と対策

- 症状: 全件の試験の途中で `Windows fatal exception: code 0x80000003`（`Garbage-collecting`）。落ちた場所は変換スレッドの中（GC が走ったのが別スレッドだっただけ）。原因は、循環参照のごみの中にあった Tk の変数・画像が、別スレッドで片付けられ、Tcl が「別のスレッドで消された」と止まること
- 影響: 実際の exe でも、変換スレッドが長く動く間に GC が走れば、確率的に起こりうる（FB02 の exe にも潜在）
- 対策: `jobs.py` で、仕事の間は GC を止め、最後の仕事が終わったとき主スレッドで集める（プロセス共通のロックつき参照数。開始の準備のどこで失敗しても戻る）。ダイアログを閉じるときも、Tk の変数と GIF のコマを主スレッドのうちに手放す。試験: GC の停止と復帰・集めるのは主スレッド・重なった仕事・開始の失敗（予約の失敗・スレッドの開始の失敗）。副作用は、変換の間（約 5〜15 秒）循環のごみがたまること（実測で影響は無い）

4. もう一度 Convert して、途中で **Cancel**（または × / Esc）を押す: ボタンが灰色になり `Cancelling...` と出て、少しして閉じる。ログに `[CANCEL]…`。出力先に作りかけの MES が残らず、既にあった MES は変わらない
5. 複数本を一覧に入れて Convert し、途中で Cancel: 終わったファイルの MES は残り、残りはやめる（ログに「どのファイルまで終わったか」）。Convert Unconverted でも同様（止めた物は一覧に残り、もう一度押せる）
6. 見て、レイアウト・文言・GIF の位置・大きさに言いたいことがあれば伝える（ダイアログの定数は `mbd2mes/progress_dialog.py` の先頭 1 か所）

## 11. 自己点検・申し送り

- **GC の落ち方は、全件の試験を回して初めて分かった**。個別の試験は通っていた（別スレッドの GC がたまたま走らなかった）。FB02 の時点で潜在していた不具合を、FB03 の試験が顕在化させた。報告書に残し、試験で固定した
- 窓の見た目は、画面に出さずに撮る道具を作って確かめた。撮った画像は見た目の確認であって、実機のモーダルの挙動（親窓の操作の遮断・フォーカス）は、らいおが exe で見るまで未確認
- 試験の置き場（`scratch/`）に `*_test.py` の名前の作業用スクリプトを置いて pytest に拾われる失敗を 1 回した（名前を直した）。Bash の heredoc 内の `\n` が半分になる環境で、置換用スクリプトが数回外れた（`Write` で書く形に直した）
- **git の状態を変える操作は一切していない**（読むだけの `log`・`diff`・`ls-files`・`check-ignore` のみ）
