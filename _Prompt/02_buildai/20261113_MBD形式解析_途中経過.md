## 分かったこと（サンプル 1 本、SHA-256 `089d0521…f9982f`）

| 項目 | 内容 | 確度 |
|---|---|---|
| byte 順 | big-endian | 実測 |
| 先頭 | `4OEL V0003`。0x70 にコース名 `suzuka` | 実測 |
| チャネル表 | 0x200〜0xDFF。1 本 48 byte で 64 本。[16:24] 名前・[24:32] 単位・[32:44] int32 の係数 A・B・C | 実測 |
| データの並び | 0x2000 から末尾まで「1 byte のタグ（＝チャネル表の番号）＋ 2 byte の値」が並ぶ。タグ 0x01（GPS）だけはタグの後に 33 byte のブロックが続く。この読み方で末尾 0xDFE667 までちょうど読み切れ、未知のタグは 0 件だった | 実測 |
| 換算式 | 物理量 = raw × A / B + C / 1000。SysV 13.7 V・水温 75 °C・LAF 9〜18 で、値がもっともらしい | 推定 |
| ヘッダのコース範囲 | 0x2C〜0x3F が緯度経度の最大と最小に見える。単位を 1/6,000,000 度とすると、緯度 34.82°・経度 136.54° で鈴鹿と合う | 推定 |
| 時刻軸 | タグ 00 とタグ 01 の件数の比は 8.0。差分記録とみる仮説がある | 未確認（サブエージェントが確認中） |

## サブエージェントの解析結果（親が再実行して検分済み）

- 1 tick = 5 ms（200 Hz）。tick はタグ 00 が出るたびに 1 つ進む。369,945 tick = 1,849.725 秒で、GPS の UTC の経過 1,849.72 秒と合う。SysV 以外は差分記録（零次ホールド）
- GPS ブロック 33 byte
  - 緯度 [2:6]・経度 [7:11]、uint32、1/6,000,000 度
  - 速度 [12:14]、0.01 km/h
  - UTC [20:23]、十進の hhmmss.cc
  - 更新は 25 Hz
- ヘッダ 0x30〜0x3F はコントロールラインの 2 点。`C:\_Tool\HRC\MBDA2\gps_p.ini` の `[suzuka.crs]` と小数 6 桁まで一致した（親も grep で確認）
- 周回 10 本は 136.2〜139.6 秒。1 周目だけ 205.4 秒（ピットアウト）。tick から出した周回時間と GPS 時刻から出した周回時間が、5 ms 以内で一致
- 未解明
  - 符号のフラグの位置（符号付きで読むべきチャネル 11 本は、当面は名前のリストで持つ）
  - THGRPADJ の換算（A=0）
  - ヘッダの一部の項目
  - PBKF・PBKR（ブレーキ圧）はセンサ未接続の疑い
- 親の修正: 疑似コードの `HEADER = 0x200` を 0x000 に直した。参照実装の所在を正本の隣に直した

## 最初の動く版（CLI。Sonnet のサブエージェントが実装し、親が検分した）

- 実行: `python -m mbd2mes <入力.MBD> -o <出力先> --date 2026-11-08`
  - 日付はファイルの中に無いので引数で指定する。省略したときは入力ファイルの更新時刻から決める
- 出力: `C:\_Prog\ECU\Logger\MBD2MES\out\26-11-8-R4.MES`
  - 58 チャネル（200 Hz、GPS は 25 Hz）と `.IXR`（ラップ）
- MES の書き出し部: RCZ2MES の commit `5b31da80…` から 8 本を写した。記録は `docs\provenance.md`、照合は `tests\test_provenance.py`
- 親が確かめたこと
  - pytest は 31 件合格・2 件 skip（実データを使う試験は環境変数で有効になる）
  - 各チャネルのファイルの大きさは、標本数 × 2 byte（緯度経度は × 4）と一致した
  - 個人情報の grep は `.bak` にしか当たらない（`.bak` は git の対象外）
- 気になる点: HED の `[GPS] Rate=10` は 2D の実物の HED から写した固定値で、GPS の実際の周期 25 Hz と合っていない。Analyzer での影響は未確認
- 仕様書の訂正: GPS 緯度の下端 34.8433635 は最初の測位の値で、実際の最小は 34.8389833（親が別のスクリプトで再計算して確認）。正本を直し、写しへ反映した
