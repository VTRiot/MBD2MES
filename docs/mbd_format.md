## 本書の読者と目的

- **読者**: `.MBD`（HRC 系の車両ロガー MBDA2 が書き出す CAN ロガーデータ）を読む処理を書く人。MBD2MES（`.MBD` → 2D Analyzer の `.MES` 変換）の実装者を第一に想定するが、**形式そのもの**の仕様として書いてあり、他の用途（解析ツール・別形式への変換）にも使える。MES 側の知見は `docs/mes_format.md` 系を見ること（本書は MES を扱わない）。
- **目的**: ファイルを正しく読み出すために必要な、構造・単位・換算・時刻軸を、確度つきで固定する。実装は §10 の擬似コードと、正本の隣の参照実装 `mbd_dump.py` にある。
- **前提**: byte 順は big-endian。数値の `0x` 表記は 16 進。オフセットは特記なき限りファイル先頭からの byte 位置。

## 1. 全体構成 [実測]

```
0x0000 .. 0x01FF   ヘッダ（512 byte）
0x0200 .. 0x0DFF   チャネル表（48 byte × 64 本 = 3072 byte）
0x0E00 .. 0x1FFF   未使用（すべて 0x00）
0x2000 .. EOF      データ（タグ付きレコードの列。ファイル末尾でちょうど読み終わる）
```

- 標本ではヘッダ＋チャネル表が、MBDA2 の設定ファイル（`SETUP/*.MBL`、8192 byte）の先頭 0x0E00 byte と同じ構造をしている。**MBD は「設定ファイルの内容（チャネル表を含む）＋記録データ」の自己完結ファイル**と読める [推定]。MBL との差は、バージョン文字（V0000 と V0003）、ヘッダの数 byte、チャネル表の内容（標本の表は並びも内容も別の構成）、MBL にだけある 0xB0〜0xC3 と 0x100〜 のコメント文。
- 標本の表は 64 本（0x3F = 最終番号）。**64 が固定か可変かは未確認**（ヘッダ 0x10 の値 0x003F が本数−1 を表すと見るのが自然だが、標本は 1 本のみ）[推定]。

## 3. チャネル表（0x200〜0xDFF）

48 byte × 64 本。番号 n の項目は `0x200 + 48·n`。**番号 n は §4 のタグと同じ**。

| 項目内オフセット | 長さ | 内容 | 確度 |
|---|---|---|---|
| [0:2] | 2 | 種別コード。CAN 入力チャネルは `0x01xx`、GPS は `0x034x`、計算チャネル（VFrSUS・VRrSUS。記録なし）は `0x021x`。下位 byte の意味は不明（0x00 が多い） | [推定] |
| [2:6] | 4 | `01 00 00 00`（全チャネル同じ） | [未確認] |
| [6:8] | 2 | CAN ID（標本では 0x06A0〜0x06AF）。GPS・計算チャネルは 0。SysV は擬似値 0x07FF | [推定] |
| [8:10] | 2 | DataMask。`FFFF`（16 bit）・`00FF`（8 bit）・`0001`（1 bit）。SysV は `03FF` | [推定] |
| [10] | 1 | 幅コード。0 = 8 bit、1 = 16 bit、2 = 特殊（GPS・SysV）。説明書の「BitDepth 8/16」に対応 | [推定] |
| [11] | 1 | CAN フレーム内の開始 bit 位置（先頭 bit からの数。8 の倍数）。同じ CAN ID の項目が重ならず 64 bit を隙間なく埋める（0x6A2・0x6A7・0x6AC・0x6AD で確認）ので、位置の読みは正しいと見てよい。16 bit はビッグエンディアン（説明書の `16(HL)` = Motorola）と読める | [推定] |
| [12:14] | 2 | 標本では「記録対象のチャネルは 0x0400、記録されないチャネル（SysV・計算チャネル）は 0x0000」。MBL では CAN チャネルも 0x0000。意味は不明（記録有効フラグか SampleTime の符号化か） | [未確認] |
| [14] | 1 | **小数点以下の表示桁数**らしい（説明書 CH Setup「Decimal point」）。Ne=0、THP=1、SysV=2。**符号の有無とは別物**（§6 参照） | [推定] |
| [15] | 1 | 計算方式。0 = Direct（生値のまま）、3 = `Y = a1·X / a2 + b`（説明書の選択肢と同じ並びの 4 番目）。A/B/C を使うのは 3 | [推定] |
| [16:24] | 8 | 名前。ASCII、`0x00` 終端。**終端後は初期化されていない残りかす**（`VFW\0F`、`LAF\0\0\0\x06\xA0` など）。`0xFE` 埋めも混じる。読むときは最初の `0x00` までで切り、末尾の `0xFE` を落とす。説明書によれば最大 8 文字 | [実測] |
| [24:32] | 8 | 単位。同様に `0x00` 終端・残りかすあり。先頭に空白が付くことがある（` PWR`）。最大 8 文字 | [実測] |
| [32:36] | 4 | A（int32、**符号付き**） | [実測] |
| [36:40] | 4 | B（int32） | [実測] |
| [40:44] | 4 | C（int32）。式の b を 1000 倍した値 | [実測] |
| [44:48] | 4 | 0 | [実測] |

- 標本の 64 本の一覧は付録（件数・生値の範囲・換算後の範囲・所見つき）。
- **チャネルの並びは標本固有**（MBL とは並びも違う）。**チャネルは番号ではなく名前（または CAN ID + 位置）で扱うこと**。
- 表にあることと記録があることは別。標本で**値レコードが 0 件**のチャネル: GPS2・KLVFI・KLVIG・DNSTLVL2・MILCODE・VFrSUS・VRrSUS（GPS1 は値レコードでなく GPS ブロックとして記録される）。**1 件だけ**のチャネル: PBKR・MODEA・MODEB・MODETYR・DSLPDEAD・KLVTCS・NTCOFTLV・KLVSRC。

## 4. データの並び（0x2000〜EOF）[実測]

### 4.1 レコード

ファイルの 0x2000 以降は、次のレコードの連続。

| 先頭 byte（タグ） | レコード全体 | 内容 |
|---|---|---|
| 0x01（GPS1） | 1 + **33** = 34 byte | GPS ブロック（§5） |
| それ以外（0x00 と 0x02〜0x3F） | 1 + **2** = 3 byte | タグ = チャネル表の番号。値は uint16（ビッグエンディアン）。8 bit のチャネルも 2 byte に拡げて入る |

- 標本ではタグが 0x40 以上のレコードは 0 件、末尾はちょうど EOF（`0xDFE667`）で読み終わる。
- GPS レコードの長さ（34 byte）の決め方に注意。**31・34・37 は 3 で割った余りが同じなので、どれでも「EOF でちょうど読み終わる」**。終端一致だけでは決まらない。決め手は次の 2 点: ① 34 のときだけ、全 tick でレコードがチャネル番号の昇順に並ぶ（§4.2）、② 31 を選ぶと GPS の直後に値 0 の偽の SysV レコードが毎回現れて tick 数が 416,186（= 369,945 + GPS 件数 46,241）に膨らみ、時刻軸（§7）が合わなくなる。

### 4.2 tick（時刻の区切り）

- **タグ 0x00（SysV）のレコードが現れるたびに 1 tick 進む**。各 tick は必ず SysV のレコードで始まる。標本の tick 数は 369,945。SysV は毎 tick 書かれる（レコード間の隔たりが常に 1）[実測]。
- 1 tick の中のレコードは、**チャネル番号の昇順**（SysV が先頭）。標本の全 tick で昇順（違反 0）[実測]。

### 4.3 差分記録 [実測]

- SysV 以外のチャネルは、**値が変わったときだけ**書かれる。標本では SysV 以外の全チャネルで、「同じチャネルの連続 2 レコードの値が等しい」ことが 0 回。ギヤ段（GearPos）は 1,850 秒で 306 レコードしかない。チャネルごとの記録間隔（tick 数）は 1・2・3… とばらつく。
- したがって**チャネルの時刻 t での値 = t 以前の最後のレコードの値（零次ホールド）**。最初のレコードより前は値なし。tick 0 には、その時点で値を持つ 37 チャネルが並ぶ（初期スナップショット）。
- 一度も値が変わらなかったチャネルは 1 件（初期値だけ）か 0 件になる。
- 内訳の目安（標本）: 全レコード 4,410,616（GPS 46,241・SysV 369,945・他の値レコード 3,994,430）。Ne 335,795 件・VFW 326,774 件・GearPos 306 件。

## 5. GPS ブロック（タグ 0x01 の後の 33 byte）

オフセットは**ブロック先頭（タグの次の byte）からの位置**。

| オフセット | 長さ | 内容 | 確度 |
|---|---|---|---|
| [0] | 1 | `0x01`（全件同じ） | [未確認] |
| [1] | 1 | ASCII `'1'`(0x31) または `'2'`(0x32)。NMEA の測位品質（1 = 単独測位、2 = DGPS 補正）に見える。標本では '2' が 83%（38,362）、'1' が 17% | [推定] |
| [2:6] | 4 | **緯度** uint32。単位 1/6,000,000 度（= 1/100,000 分）。標本 34.8389833° 〜 34.8484118°（最初の測位は 34.8433635°） | [実測] |
| [6] | 1 | ASCII `'N'`（全件）。南緯は `'S'` と推定（南緯・西経の標本は無い） | [推定] |
| [7:11] | 4 | **経度** uint32。同じ単位。標本 136.5219588° 〜 136.5434030° | [実測] |
| [11] | 1 | ASCII `'E'`（全件）。西経は `'W'` と推定 | [推定] |
| [12:14] | 2 | **速度** uint16。単位 **0.01 km/h**。最大 29,322 = 293.22 km/h | [実測] |

| [16:18] | 2 | `02 02`（全件） | [未確認] |

| [19] | 1 | 0（全件） | [未確認] |
| **[20:23]** | 3 | **UTC 時刻**（uint24）。**十進の `hhmmss.cc`**（時分秒＋百分の一秒）として読む（`c%100` = 百分秒、`(c/100)%100` = 秒、`(c/10000)%100` = 分、`c/1000000` = 時）。測位 1 回ごとに 4（= 0.04 秒）進む。値の例: 564360 → 00:56:43.60、1273332 → 01:27:33.32 | [実測] |
| [23] | 1 | 0（全件） | [未確認] |

- **単位の根拠（別の出どころ）**: ① ヘッダのコントロールラインが `gps_p.ini` の値と一致（同じ単位）、② 位置の差分から出した速度と [12:14] の比の中央値が 100.0（0.01 km/h 単位）、③ 1 周の経路長が 5.73 km（鈴鹿のフルコース公称 5.807 km に対し −1.3%。GPS 点列の弦長なので少し短く出るのは自然）。
- **更新周期**: 常に時刻が 4（0.04 秒）進む → **25 Hz**。標本の測位 46,241 回のうち、4 以外の刻みは分・時の繰り上がりを除くと「8 が 3 回」（欠測）だけ [実測]。
- **時刻の繰り上がりに注意**: 十進表記なので、`mmss` が 59.96 → 60.00 に当たる所で値が 4004 飛び（標本で 30 回）、時が上がる所で 404004 飛ぶ（1 回）。差を取るときは必ず上の式で秒に直してから引くこと。uint24 は 16,777,215 まで。UTC 16:46 以降（日本時間 翌 01:46 以降）は収まらない [推定：未観測]。
- チャネル `GPSspd`（タグ 0x07）は**ブロック内の速度と同じ値**の再掲（標本で、同じ tick の値と 45,616 件すべて一致。ブロックの速度が変化した回にだけ書かれる）。`GPS2`（タグ 0x02）は標本に記録なし。

## 6. 換算式

### 6.1 CAN 系チャネル（種別 `0x01xx`）[実測]

```
物理量 = 生値 × A / B + C / 1000        （[15] = 3 のとき。生値は符号付き/なしに解釈してから）
```

- A・B・C はチャネル表の int32。式は説明書の `Y = a1·X / a2 + b`（b = C/1000）と同じ。[15] = 0 のチャネル（Ne、GearPos、各種ステータス）は A = B = 1 で、**生値がそのまま物理量**。
- 標本の主要チャネルの結果は妥当（付録の「所見」欄）。主な確認:
  - **VFW / VRW**（前後輪速度、A/B = 1/128）: GPS 速度との比の中央値が 0.993 / 1.019。
  - **GYROAN**（バンク角、A/B = 1/200）: GPS の位置から出した横加速度の傾き（`atan(v·ψ'/g)`）と相関 **0.989**、傾き比 1.09（タイヤの厚み分だけ実バンクが深い）。**右が正**。
  - **GYXAC**（前後加速度 [G]）: GPS 速度の微分と相関 0.917、傾き 1.07。**前進加速が正**。
  - **GearPos**: 段別の rpm / (km/h) が 1 速 110.6 → 2 速 87.0 → 3 速 73.4 → 4 速 62.1 → 5 速 54.5 → 6 速 48.5 と単調。0 は中立。
  - **FCTOTAL**（積算燃料 [cc]、A/B = 0.65536）: 単調非減少、19 → 9,459 cc（30.8 分）。
  - SysV 13.4〜14.1 V、TW 69〜96 degC、TA 20〜28 degC、Ne 1,395〜14,973 rpm、LAF 9.5〜16.5。
- **Ne は A/B/C に依らず生値 = rpm**（A = B = 1）。付属レイアウト `stdgp.ini` のグラフ範囲は内部で 1000 倍の値を使っている（別の話）。

### 6.2 符号（int16 か uint16 か）[未確認：決め手がテーブル内で特定できていない]

- 値は 2 byte 固定だが、**符号付きで読むべきチャネルがある**。標本では、符号付きにすると物理的に妥当になり（正負が出る・int16 の端に飽和する）、符号なしだと非現実的になるチャネルが 11 本: GYROAN、SLIP、DSLIP、GYPIAN、PIANWIL、GYPIRA、GYXAC、SLIPTRG、SLPTRGOF、SLPTRGEB、IGTRQRTD。
- 逆に **符号なしでないと困る**16 bit チャネル: VFW・VRW・VSPEST（生値が 32,767 を超える）、KLFWGYAJ・KLRWGYAJ・KSRCROAN（32,768 = 係数 1.0）。
- 標本では **[14] ≥ 5 のチャネルが上の 11 本とちょうど一致**する（他は [14] ≤ 4）。ただし [14] は小数点以下の桁数の設定と読むのが自然で、符号の有無を直接表す欄ではない。**一致は桁数の取り方の偶然かもしれない**（MBL では GYROAN の [14] が 6、標本では 5 と、設定ファイルごとに値が違う）。
- **実装の指針**: 当面は「チャネル名ごとの符号付きリスト」を持ち、[14] ≥ 5 の規則との**両方が一致することを検査**する。別の標本で食い違いが出たら本節を直す。符号の真の格納場所は 2 本目以降の標本（と、MBDA2 の画面値との照合）で確かめる必要がある。

### 6.3 特別扱いが要るもの

| チャネル | 扱い | 確度 |
|---|---|---|
| GPSspd（#7） | 表の A/B（1000/1000）は効かない。**0.01 km/h 単位**（生値 ÷ 100 = km/h）。GPS ブロックの速度と同値 | [実測] |
| THGRPADJ（#6） | **A = 0** で式が成立しない。生値 0〜578、B = 584,000。`生値 × 1000 / 584000`（= 0〜0.99）のような正規化の可能性はあるが、裏付け無し。**未解明**として生値を持ち回る | [未確認] |
| PBKF・PBKR（#20, #21） | 件数は 35・1、値は 249/250・255 のまま（A/B で 12.2・12.5 MPa）。**センサ未接続の疑い**。換算は式どおりだが物理量としては使えない | [推定] |

## 7. 時刻軸

### 7.1 結論 [実測]

- **1 tick = 5 ms（200 Hz）**。時刻 `t = tick × 0.005 秒`（tick は §4.2 の 0 始まりの番号）。標本の長さは 369,945 tick = 1,849.725 秒。
- **GPS 時刻（UTC）との対応**: 標本の GPS 時刻の経過は 1,849.72 秒（00:56:43.60 → 01:27:33.32）。tick 数 × 5 ms と **0.005 秒の誤差**で一致。GPS 時刻 − tick × 0.005 の最小二乗の傾きは 5.00016 ms/tick（+31 ppm）、各 GPS ブロックの当てはめ残差は −31 〜 +7 ms。
- 別の出どころ（周回時間）による確認: ヘッダのコントロールライン（`gps_p.ini` と一致）を GPS 軌跡が横切る 11 回の間隔は、**tick 数から出した時間と GPS 時刻の差から出した時間が、10 周すべてで 5 ms 以内に一致**（周回時間 136.2〜139.6 秒。1 周目は 205.4 秒＝ピットアウト後の周回）。周回時間の絶対値は鈴鹿のフルコースの妥当な値。

### 7.2 解釈

- **各チャネルの時刻の決め方**: そのレコードが現れた tick の時刻（`tick × 5 ms`）。差分記録なので、書かれていない tick は直前の値を保つ（§4.3）。固定レートの時系列（MES など）が要るなら、tick（200 Hz）または任意の間隔に零次ホールドで標本化する。
- **GPS の時刻**: tick 時刻とは別系統の UTC。UTC と tick の対応は `UTC(tick) = UTC(tick 0) + tick × 5 ms`。tick 0 の UTC は、全 GPS ブロックの `utc − tick × 0.005` の中央値（標本で 3403.655 秒 = 00:56:43.655）。**GPS ブロックが tick 列のどこに置かれるかには ±数十 ms のばらつきがある**（隣り合う GPS ブロックの間は 3〜15 tick で、99.9% が 6〜11 tick、最頻 8）。測位は厳密に 40 ms 刻みなので、これは「GPS の受信が tick 列へ入る遅れのばらつき」と読める。**tick の間隔そのものが厳密に一様か、ばらつきの源が tick 側かは、標本からは決められない** [未確認]。
- 5 ms という値が設定（説明書の SampleTime。例「送信間隔 10 ms → 5 ms 設定」）なのか固定なのか、ファイル内のどこに格納されているかは**未確認**（§3 の [12:14] が候補）。別の標本で tick と GPS 時刻の比を測って確かめること。
- 連続性: GPS の時刻に欠測らしい飛びは 3 回（4 → 8）だけ。30 分間の途中に記録の中断は無い [実測]。
- **ラップ**: ヘッダのコントロールラインを軌跡が横切った時刻（GPS ブロックの位置の線分交差）から出せる。ファイルにラップタイムのレコードは見当たらない（GPS ブロックにもチャネルにも）[実測：見当たらないこと]。1 つ注意: MBDA2 は画面上でフィニッシュラインを動かせる（説明書）。**ヘッダの線が記録時の線か、保存時に書き換えられた線か**は区別できない。

HEADER, TABLE, DATA = 0x000, 0x200, 0x2000
TICK_S, GPS_TAG, GPS_BLOCK = 0.005, 1, 33

def u16(b, o): return int.from_bytes(b[o:o+2], 'big')
def u32(b, o): return int.from_bytes(b[o:o+4], 'big')
def s32(b, o): return int.from_bytes(b[o:o+4], 'big', signed=True)

for n in range(64):                       # 本数はヘッダ 0x10 + 1（標本では 64）
    e = d[TABLE + 48*n : TABLE + 48*(n+1)]
    name = e[16:24].split(b'\0')[0].rstrip(b'\xfe').decode('ascii')
    A, B, C = s32(e, 32), s32(e, 36), s32(e, 40)
    ch.append((name, A, B, C))

def to_physical(i, raw, signed):          # signed は §6.2 のリストで決める
    name, A, B, C = ch[i]
    v = raw - 65536 if signed and raw >= 32768 else raw
    return v * A / B + C / 1000 if A and B else v   # GPSspd は別（÷100）

def utc_seconds(c):                       # 十進 hhmmss.cc
    return (c // 1000000) * 3600 + (c // 10000 % 100) * 60 + c // 100 % 100 + c % 100 / 100

p, tick = DATA, -1
while p < len(d):
    tag = d[p]
    if tag == 0:
        tick += 1                          # 1 tick = 5 ms
    if tag == GPS_TAG:
        b = d[p+1 : p+1+GPS_BLOCK]
        lat = u32(b, 2) / 6_000_000        # b[6] = 'N'
        lon = u32(b, 7) / 6_000_000        # b[11] = 'E'

        utc = utc_seconds(int.from_bytes(b[20:23], 'big'))
        p += 1 + GPS_BLOCK
    else:
        raw = u16(d, p+1)                  # (tick*TICK_S, tag, raw) = チャネル tag の変化点
        p += 3
